# Git в SaaS

Git поддерживает два типа подключения в SaaS: управляемое зеркало HTTPS-источника
и внешний репозиторий только для чтения. Тип подключения и разрешенные действия
возвращаются в API, интерфейс не определяет их по имени клиента или пути.

Нервион не принимает push и не предоставляет SSH Git-сервер. У внешних
репозиториев действующие push, clone и deployment hooks продолжают работать
вне backend Нервиона. Backend не получает их SSH-ключи и не выполняет hooks.
Submodules, Git LFS, внешний diff и textconv не поддерживаются.
Прежний self-hosted режим сохраняется при `TENANCY_ENABLED=false`.

## Настройка оператора

- Установить поддерживаемую исправленную версию Git не ниже 2.45.
- Создать отдельное постоянное хранилище `GIT_TENANT_ROOT`. Все backend-реплики
  и workers используют один и тот же volume и путь. Каталог принадлежит сервисной
  учетной записи. Пользователи не получают файловый доступ к нему.
- Задать `GIT_ALLOWED_HOSTS`: точные имена публичных Git-провайдеров через запятую.
  Пустой список запрещает подключение новых источников. Маски не поддерживаются.
- Задать секрет `GIT_CREDENTIAL_KEY`: 32 случайных байта в стандартном base64.
  Ключ общий для backend и workers, хранится вне репозитория. Потеря ключа делает
  сохраненные подключения недоступными. Ротация требует отдельного
  перешифрования, простая замена значения не подходит.
- Включить `featureFlags.git=true` у нужного пространства.
- Запустить tenant worker с обработчиком `git.cleanup` для удаления старых копий.

Лимиты по умолчанию: `GIT_MAX_REPO_BYTES=536870912` (512 MiB на копию),
`GIT_MAX_TENANT_BYTES=2147483648` (2 GiB на пространство вместе с временными
копиями), `GIT_MAX_REPOS_PER_TENANT=25`. Один Git-процесс ограничен 20 секундами
и 64 MiB вывода. Одновременно выполняется одна изменяющая Git-операция на
пространство. Для больших репозиториев нужен отдельный фоновый импорт, а не
увеличение HTTP-транзакции без ограничения.

Квота проверяется во время записи каждые 500 мс, поэтому это не жесткий
дисковый барьер. На volume нужны собственная квота и мониторинг свободного
места. На обновление требуется место для второй копии репозитория.

Подключение разрешено только по HTTPS на стандартном порту. URL не содержит
учетных данных, query или fragment. Каждый сетевой вызов повторно проверяет
allowlist и все DNS-адреса, затем закрепляет выбранный публичный IP через
`http.curloptResolve`. Узкий локальный CONNECT proxy дополнительно пропускает
только этот hostname и соединяется только с проверенным IP. Это закрывает
переходы к сторонним адресам через Git HTTP alternates, а не только redirects.
Перенаправления, наследуемые proxy, credential helpers
и конфигурация Git пользователя отключены. TLS-сертификат проверяется по
исходному имени провайдера. Внешний egress-фильтр рекомендуется как второй
уровень защиты.

## Данные и учетные записи

Каталог создается сервером:

```text
GIT_TENANT_ROOT/tenants/{tenantId}/{repositoryKey}/
  repository.git/
  connection.enc
```

`repositoryKey` генерируется сервером. Запрос не может передать путь.
`connection.enc` содержит URL, имя пользователя и токен, зашифрованные
AES-256-GCM с привязкой к tenant и repositoryKey. Токен передается Git
через окружение дочернего процесса, не через URL или аргументы командной
строки. Git stderr не возвращается клиенту и не записывается в журнал.
Общие глобальные SSH-ключи и `GIT_CLONE_BASE_URL` в SaaS не используются.

Оператор должен исключить тела запросов `/api/git/repos` из access/debug/APM
логов. Используйте токены только для чтения выбранного репозитория.
Доступ к хранилищу и окружению процессов разрешен только сервисной учетной
записи и операторам. Резервное копирование должно согласованно включать data
database, этот volume и отдельную резервную копию ключа шифрования.

API:

- `POST /api/git/repos`: `name`, `remoteUrl`, необязательные `username`,
  `token`, `defaultBranch`, `projectId`. Доступно администратору пространства.
- `POST /api/git/repos/:id/fetch`: получить актуальные ветки и теги из
  сохраненного источника.
- `DELETE /api/git/repos/:id`: отключить репозиторий и поставить его
  tenant-копию в очередь очистки. Удаленный источник не меняется.
- Существующие endpoints чтения сохраняются. Read-only запрещает connect,
  fetch и delete, но позволяет читать уже загруженные данные.

Fetch работает с новой копией. Ссылка в БД меняется в текущей tenant-транзакции.
Откат удаляет новую копию. Предыдущая версия удаляется отдельным tenant job
не ранее чем через две минуты после commit. При остановленном worker,
блокировке или read-only очистка откладывается. После аварийного завершения
процесса возможны неиспользуемые копии, для них предусмотрена сверка.

## Внешние репозитории только для чтения

Этот режим сохраняет существующее Git-хранилище и его внешнюю схему публикации.
Исходные каталоги не копируются, не переносятся и не очищаются. После внешнего
push новые коммиты доступны при следующем чтении страницы Нервиона.

1. Подключите исходный каталог к backend отдельным read-only mount. Укажите
   этот абсолютный путь в `GIT_EXTERNAL_ROOT`. Нужна защита mount средствами
   Linux, одних файловых permissions недостаточно. Используется один корневой
   bind mount; любые вложенные mounts запрещены, включая read-only aliases.
   Root не должен пересекаться с `GIT_TENANT_ROOT`.
2. Задайте `GIT_EXTERNAL_REPOSITORIES_JSON` явным массивом привязок:

```json
[
  {
    "tenantId": "11111111-1111-4111-8111-111111111111",
    "repositoryId": 7,
    "gitdir": "/external-git/example.git",
    "cloneUrl": "ssh://git@git.example.com/repos/example.git"
  }
]
```

3. `tenantId`, числовой ID и сохраненный в БД `gitdir` должны одновременно
   совпасть с конфигурацией. HTTP API не принимает эти привязки. Один каталог
   может иметь несколько записей только внутри одного tenant. Делить каталог
   между клиентами нельзя.
4. `cloneUrl` необязателен. Укажите его только после проверки адреса и прав
   доступа. Это адрес для пользователя, backend никогда не обращается к нему.
   Глобальный `GIT_CLONE_BASE_URL` не подставляется. Пароли, токены и параметры
   в адресе запрещены.
5. Включите `featureFlags.git`. Проверьте просмотр веток, истории, дерева,
   текстовых и бинарных файлов, diff и обновление после внешнего push.

Чтение выполняется через отдельный адаптер с чистой временной Git-конфигурацией
и разрешенным набором команд. Исходная конфигурация не используется для запуска
Git. Symlink, alternates, include и shared-worktree layouts отклоняются.
Hooks, внешние diff/textconv, fsmonitor, credentials и сеть отключены.
Временные данные создаются отдельно; исходный каталог остается read-only.

Обычные файлы Git-объектов могут иметь hardlinks. Такой формат используется
при [локальном клонировании Git](https://git-scm.com/docs/git-clone).
Чтение идет по имени внутри разрешенного object store, другие имена hardlink
не обходятся. Для `HEAD`, config, refs и packed-refs hardlinks запрещены.

Исходная файловая система управляется доверенным оператором. Пользователи
других пространств не должны иметь возможности менять ее файлы, в том числе
через writable hardlink aliases. Read-only mount ограничивает backend, но не
оператора источника. Этот режим не предназначен для размещения произвольно
изменяемых клиентами каталогов на общей файловой системе.

Проверка одного каталога ограничена 5 секундами и 250 000 файловых записей.
Для refs действуют пределы 25 000 записей и 16 MiB метаданных. Подготовка
временного представления также ограничена 5 секундами. Один backend-процесс
выполняет до четырех таких операций одновременно, очередь содержит не более
32 запросов. При превышении лимитов источник считается недоступным;
ограничения Git-процесса остаются 20 секунд и 64 MiB вывода.

Для внешнего репозитория backend запрещает `fetch`, отключение через `DELETE`
и очистку исходного каталога. Интерфейс скрывает эти действия, но серверные
проверки не зависят от интерфейса. Migration job также получает ту же конфигурацию
и пропускает точные внешние привязки. Попытка импортировать иной путь внутри
внешнего root завершается ошибкой, а не созданием статической копии.

Если каталог отсутствует или не прошел проверку, запись остается в списке со
статусом "Недоступен". Остальные репозитории продолжают открываться. API не
раскрывает пути или сообщения Git. При открытии недоступной записи предыдущие
коммиты и файлы очищаются. Выбор без явного ID предпочитает доступную запись.

Публичный `GitRepoListItem` содержит `mode` (`managed`, `external_read_only`,
`self_hosted`), `availability` и `capabilities` (`canRead`, `canFetch`, `canDelete`).
Возможности отражают доступность хранилища и режим чтения tenant. Они не заменяют
проверки авторизации, участия в пространстве и доступа к проекту.

Внешние репозитории резервируются вместе с их исходной системой, отдельно от
управляемого Git volume. Этот адаптер не добавляет HA, backup или авторизацию
в существующий SSH-сервер и не превращает его в tenant-aware Git-хостинг.

## Перенос существующих репозиториев

Сначала выполнить tenant-миграции БД и зарегистрировать первого клиента.
До переноса старый абсолютный `gitdir` не читается в SaaS, если он не зарегистрирован
как внешний read-only источник по разделу выше. Глобального fallback нет.
Для действующего SSH-хостинга с deployment hooks выбирайте внешний источник,
а не импорт статической копии.

1. Сделать backup БД и исходных репозиториев. Остановить изменение репозиториев,
   backend и workers на время применения.
2. Указать `TENANCY_BOOTSTRAP_TENANT_ID`, `GIT_TENANT_ROOT`,
   `GIT_CREDENTIAL_KEY` и отдельные `MIGRATION_POSTGRES_HOST`,
   `MIGRATION_POSTGRES_PORT`, `MIGRATION_POSTGRES_USER`,
   `MIGRATION_POSTGRES_PASSWORD`, `POSTGRES_DB`.
3. В `GIT_MIGRATION_SOURCE_ROOTS` перечислить через запятую точные абсолютные
   каталоги-родители исходных репозиториев. Корень файловой системы и домашний
   каталог запрещены. Symlink, alternates и shared worktree требуют отдельного
   предварительного standalone export.
4. Запустить просмотр плана:

```bash
pnpm --filter backend tenant:git:migrate --dry-run
```

5. После проверки задать `GIT_MIGRATION_WRITES_STOPPED=true` и выполнить:

```bash
pnpm --filter backend tenant:git:migrate --apply
```

Создается новая независимая bare-копия без hardlinks. Исходный репозиторий,
его hooks, credentials и config не меняются. Сохраняются история, ветки и
теги; используется чистая конфигурация. Импортированная копия доступна для
чтения, без удаленного источника и без переноса глобальных credentials.
Для дальнейшей синхронизации подключите HTTPS-источник как новый репозиторий.

Повторный запуск пропускает уже перенесенные копии. Если обновление БД
завершилось неопределенно, отдельная новая копия остается на диске до сверки.
Для очистки неиспользуемых копий старше двух часов:

```bash
pnpm --filter backend tenant:git:migrate --prune-orphans --dry-run
pnpm --filter backend tenant:git:migrate --prune-orphans --apply
```

Применение очистки также требует остановленных записей и
`GIT_MIGRATION_WRITES_STOPPED=true`. Удаляются только серверные UUID-каталоги
выбранного tenant, на которые больше не ссылается `repos`. Эти копии после
удаления восстанавливаются только из backup или повторным импортом.
