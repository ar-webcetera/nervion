# Мониторинг сайтов в SaaS

Модуль проверяет HTTP-статус публичного сервиса. Настройки, результаты,
фоновые задания и сообщения в чате ограничены текущим пространством через
tenant context и RLS. Управление доступно администратору пространства.

## Подключение

1. Указать `HEALTHCHECK_ALLOWED_HOSTS`: точные DNS-имена через запятую.
   Пустой список запрещает добавление целей. Маски и разрешение всех хостов
   не поддерживаются. Общий список задает оператор, клиент его не меняет.
2. При необходимости задать `HEALTHCHECK_TENANT_LIMIT` (по умолчанию 100).
   Создание монитора берет транзакционную блокировку клиента перед проверкой
   количества, поэтому параллельные запросы не обходят лимит.
3. Включить `featureFlags.healthchecks=true` в настройках клиента.
4. Создать монитор в разделе мониторинга. Указать URL, ожидаемый код,
   интервал, таймаут, чат и отправителя уведомлений. Администратор и выбранный
   отправитель должны состоять в этом чате. Для уведомлений нужен модуль чата.

Разрешены HTTP/HTTPS на стандартных портах 80/443. Учетные данные в URL,
fragment, IP вместо hostname, localhost и приватные сети запрещены.
Максимальный таймаут 30 секунд в SaaS и self-hosted, интервал от 30 секунд до суток.
API и форма используют общий лимит. При переносе мониторов настроенные
30 секунд сохраняются без изменения; значение по умолчанию остается 10 секунд.
URL с query допустим, но не размещайте в нем секреты: адрес виден в интерфейсе
и уведомлениях чата.

## Выполнение и ограничения

Планировщик выбирает просроченные проверки внутри tenant-транзакции и
создает задания `healthchecks.probe`. Отдельных таймеров на числовой ID
монитора в SaaS нет. Перед выполнением worker проверяет клиентский статус,
feature flag и shard. Строка монитора блокируется, чтобы реплики не
выполняли одну проверку параллельно.

Перед каждым запросом разрешаются все DNS-адреса цели. Если среди них есть
непубличный адрес, запрос запрещается. Соединение устанавливается напрямую
с выбранным проверенным IP; исходное имя сохраняется для Host и TLS.
Повторного DNS lookup, автоматического redirect и proxy из окружения нет.
Читаются только статус и ограниченные заголовки, тело ответа не загружается.
DNS ограничен тремя секундами, сама HTTP-проверка ограничена таймаутом.
Это укладывается в 60-секундный лимит простоя tenant-транзакции. Блокировка задания
удерживается до завершения транзакции, без истекающей во время запроса lease.

Код 301/302 считается обычным результатом, перехода по Location нет.
Если нужно проверять конечную страницу, укажите ее URL напрямую.
Ошибочный сертификат HTTPS считается недоступностью, отключить проверку
сертификата через клиентский API нельзя.

При смене статуса отправляется сообщение в настроенный чат этого клиента.
При удалении отправителя из чата уведомление не отправляется. Read-only,
блокировка клиента или выключенный модуль прекращают новые проверки.
Последний сохраненный результат остается доступен при read-only.

Завершенные задания мониторинга хранятся один час и очищаются небольшими
порциями внутри tenant context. Ошибочные задания и задания других модулей
не затрагиваются. Монитор хранит последний результат, это не журнал
истории доступности и не расчет SLA.

Интервал задает срок следующей постановки в очередь, а не гарантированное
время запуска под любой нагрузкой. Следите за возрастом pending jobs,
длительностью проверок и пулом соединений. Worker обрабатывает ограниченную
порцию каждого клиента; при росте очереди добавляются backend/worker-реплики.
Сетевой egress firewall рекомендуется как второй уровень защиты.

## Приемка на изолированном стенде

Проверить два клиента с одинаковыми локальными ID мониторов, запрет чужого
чата, конкурентное создание сверх квоты, disabled/read-only, два workers,
public/private смешанные DNS-ответы, DNS rebinding, таймаут и redirect
на внутренний IP. Реальные внешние цели подключаются отдельно оператором.

Тесты `public-endpoint.spec.ts`, `healthchecks.tenant.spec.ts` и
`tenant.middleware.spec.ts` используют моки и не обращаются к сайтам клиентов.
Их наличие не означает, что приемочный прогон уже выполнен.

Основание сетевой политики: [OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).
