# Почта в SaaS

Почта использует общий backend, SMTP-приемник и S3. Почтовые таблицы и очередь отправки изолированы RLS. Домены и ключи Postbox задает оператор. Публичного подключения доменов нет.

## Подключение клиента

1. Применить tenant migration `1793500000000-TenantMailOutbox` отдельной migration-ролью. Она добавляет `mail_outbox`, составной внешний ключ, `FORCE ROW LEVEL SECURITY` и статусы писем.
2. Подтвердить владение доменом через DNS. Проверить домен в Yandex Postbox и настроить DKIM, SPF, DMARC. Оператор не должен добавлять домен только по заявлению клиента.
3. Создать отдельный сервисный аккаунт Postbox клиента и статический ключ с минимальным правом отправки. [Требования Yandex Postbox](https://yandex.cloud/ru/docs/postbox/operations/send-email).
4. Добавить запись в серверный секрет `MAILBOX_TENANTS_JSON`. Она должна одинаково присутствовать на всех API-репликах и SMTP-воркерах. Секрет не возвращается через API и не попадает в репозиторий.
5. Включить feature flag `mail` и создать нужные ящики в разделе "Почтовые ящики" пространства. Неизвестные или отключенные ящики не принимают почту. Автоматическое создание входящих ящиков и catch-all в SaaS отключены.
6. Направить MX домена на SMTP-приемник. Для вложений требуется рабочий приватный S3. SMTP возвращает временную ошибку, если raw-письмо нельзя сохранить.
7. Настроить передачу событий Postbox на `https://admin.nervion.ru/api/mailbox/postbox-events/{webhookRoutingKey}` с `Authorization: Bearer {webhookSecret}`. Каждое подключение имеет отдельный маршрут и секрет. Триггер не должен смешивать события клиентов в одну доставку.

Production SMTP требует `SMTP_TLS_CERT_FILE` и `SMTP_TLS_KEY_FILE`, пути к смонтированным сертификату и приватному ключу почтового хоста. Без них SaaS SMTP не запускается. Сертификат обновляется вне приложения, затем приемник перезапускается. Приемник поддерживает STARTTLS, ограничивает число соединений до 20 и закрывает неактивные соединения через 60 секунд.

Формат записи без реальных секретов:

```json
[
  {
    "tenantId": "11111111-1111-4111-8111-111111111111",
    "domainOwnershipVerified": true,
    "domains": ["mail.customer.example"],
    "notificationAccount": "bot@mail.customer.example",
    "taskAliasAccount": "support@mail.customer.example",
    "accessKeyId": "replace-in-secret-manager",
    "secretAccessKey": "replace-in-secret-manager",
    "configurationSet": "customer-events",
    "webhookRoutingKey": "22222222-2222-4222-8222-222222222222",
    "webhookSecret": "replace-with-independent-random-32-plus-character-secret"
  }
]
```

Домены должны быть строчными и глобально уникальными. Один домен нельзя подключить двум клиентам. `notificationAccount` обязателен; `taskAliasAccount` опционален. Все указанные адреса должны относиться к доменам этой записи. Ключи `POSTBOX_*`, `MAILBOX_DOMAIN` и общие служебные адреса остаются только для legacy-режима, SaaS к ним не обращается.

Секреты обновляются через secret manager и перезапуск реплик. Endpoint Postbox в SaaS фиксирован: `https://postbox.cloud.yandex.net`, регион `ru-central1`. Пользователь не может направить отправку и ключи на произвольный URL.

## Отправка и сбои

API сохраняет письмо и запись очереди одной транзакцией. Интерфейс показывает "в очереди", затем "отправляется" и результат. Несколько реплик выбирают работу через `FOR UPDATE SKIP LOCKED`. Claim отправки фиксируется отдельной транзакцией до сетевого вызова.

У [SendEmail Yandex Postbox](https://yandex.cloud/en/docs/postbox/aws-compatible-api/api-ref/send-email) нет документированного idempotency token. Поэтому SDK не повторяет сетевые вызовы автоматически. Нельзя обещать exactly-once доставку SMTP.

- Ошибка подготовки или явный HTTP 4xx от Postbox: письмо получает `failed`, доступна ручная повторная отправка.
- Обрыв связи или сбой БД после возможного приема: `uncertain`, автоматической повторной отправки нет. Интерфейс показывает "статус уточняется".
- Завершение процесса после claim: через 15 минут оставшийся `sending` становится `uncertain`, но не отправляется заново.
- Подтвержденное событие Postbox связывается с исходным Message-ID и снимает неопределенность. Оператор проверяет события провайдера до любых ручных действий с таким письмом. Повторная отправка через API для `uncertain` запрещена, чтобы не создавать незаметные дубли.

Очередь хранит ссылки на письма, а не ключи провайдера. Уведомления также ставятся в очередь после сохранения; Message-ID включает tenant ID. При блокировке или read-only новые отправки не выполняются. Входящий SMTP для read-only отвечает временной ошибкой, отправляющий сервер сможет повторить доставку после восстановления доступа.
Перед внешней отправкой повторно проверяются статус клиента, доступ отправителя
к пространству и ящику. Системные письма без пользовательского actor разрешены
только от настроенного `notificationAccount`. Уже принятый провайдером запрос
нельзя отозвать переключением read-only. Незавершенные claims заблокированного
клиента обрабатываются после возобновления, без обхода режима чтения.

## Входящая почта и файлы

SMTP определяет tenant только по подтвержденному домену envelope recipient. Для каждого пространства открывается собственная транзакция. Совпадающие числовые ID ящиков не смешиваются. Внешний заголовок `X-Nervion-Notification-Id` не считается доверенным и в SaaS игнорируется.

Повторные входящие с одинаковым Message-ID сериализуются и дедуплицируются в пределах ящика. При отсутствии Message-ID используется хеш raw-письма. Вложения и raw сохраняются через `StorageService` под `tenants/{tenantId}/...`. Максимальный SMTP-размер составляет 25 МБ, исходящие вложения ограничены 7 МБ по фактическому размеру S3-объектов.

Пользователь может приложить свою новую загрузку либо вложение ящика, к которому у него есть доступ. Произвольные пути другого пространства и закрытого ящика отклоняются.

## Проверки перед включением

Unit-проверки конфигурации, SMTP-маршрутизации и durable outbox прошли локально
2026-10-30. На отдельном PostgreSQL проверены миграция outbox, одинаковые ID
двух пространств, RLS, составные FK и каскадное удаление.

До подключения реального клиента нужны staging-проверки с тестовым доменом:
MX и TLS, Postbox, события, read-only, отказ S3, падение процесса после claim
и повтор webhook. Реальные письма в ходе реализации и локальных тестов не отправлялись.
