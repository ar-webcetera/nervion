# SaaS в одном PostgreSQL-кластере

Режим включается через `TENANCY_ENABLED=true`. До миграции оставьте значение `false`.
Одна сборка frontend и backend обслуживает все пространства. Поддомен определяет
клиента, `nervion_platform` хранит клиентов и доступы, `nervion_data_1` хранит рабочие
данные с обязательным `tenant_id`. Обе базы могут находиться в одном PostgreSQL 17.

Backend не запускает production-миграции при старте. Они выполняются отдельным
заданием до запуска приложения. Стандартный `docker-compose.yml` содержит такое
задание `migrate`; локальные dev-серверы запускаются через pnpm.

## Доступные функции и срок лицензии

Основные разделы включены, пока соответствующий флаг не установлен в `false`.
Форма настроек показывает эти значения и при отсутствии ключей в `featureFlags`.
Отключенные разделы скрыты в десктопном и мобильном меню, запрещены по прямым
ссылкам и в API. Флаг `tasks` также управляет календарем и планированием.
Если задачи выключены, после входа открывается первый доступный раздел с учетом
роли пользователя. Если доступных разделов нет, отображается страница отказа
в доступе без повторяющихся перенаправлений.

В SaaS доступны задачи, проекты, пользователи, файлы, чат, wiki, CRM и отчеты.
Почта, Git, голос и мониторинг сайтов включаются отдельно через `featureFlags`
в модалке настроек пространства: `mail`, `git`, `voice`, `healthchecks`.
Для этих четырех модулей нужно именно значение `true`; отсутствующий флаг
не дает доступ. У новых и перенесенных пространств они изначально выключены.
Сначала оператор настраивает подключения по инструкциям
[почты](./saas-mail.md), [Git](./saas-git.md), [голоса](./saas-voice.md) и
[мониторинга](./saas-monitoring.md). Флаг сам по себе не создает почтовый домен,
TURN-сервер, Git volume или разрешения на исходящие запросы.
Вход работает по email и паролю. Демо-вход в SaaS недоступен.
Вход через Яндекс можно отдельно включить для пользователей, у которых до
переноса уже сохранен `yandex_id` в этом пространстве. Новые аккаунты не создаются,
совпадение email не привязывает учетную запись, membership должен быть активен.

Для включения задайте `YANDEX_OAUTH_CLIENT_ID`, `YANDEX_OAUTH_CLIENT_SECRET` и
`YANDEX_OAUTH_TENANT_HOSTS` со списком точных hostname через запятую. Wildcard
не поддерживается. В настройках приложения Яндекса заранее зарегистрируйте
`https://<hostname>/api/auth/yandex/callback` для каждого разрешенного hostname.
Без allowlist кнопка в SaaS скрыта. Frontend получает доступные способы входа
через `/api/auth/providers`; идентификатор приложения и секрет туда не попадают.
State привязан к пространству и hostname, действует десять минут, защищен
подписью, PKCE S256 и отдельными host-only Secure/HttpOnly cookies.

При смене канонического домена сначала зарегистрируйте новый callback и
проверьте вход на нем. Редирект страниц со старого домена не заменяет настройку
OAuth, API, WebSocket и webhook. Host-only сессия между доменами не переносится,
поэтому пользователю потребуется заново войти.

После `paid_until` действует семь дней grace period, затем пространство становится
read-only. Вход и чтение сохраняются, запись и фоновые изменения запрещены.
Активные человеческие аккаунты, включая администраторов и гостей, занимают места.
Незавершенная активация временно резервирует место, чтобы параллельные запросы не
превышали лимит. Оплата отмечается оператором вручную, публичной регистрации нет.

При отмене устанавливается `retention_until` через 90 дней, доступ становится
read-only. Автоматического purge нет. По окончании срока оператор отдельно
подтверждает удаление конкретного tenant, проверяет срок хранения и backup,
удаляет его строки и S3 namespace и сохраняет запись в платформенном аудите.
Нельзя удалять общую Identity, если она используется другим пространством.
Эта операция выполняется отдельной процедурой с проверкой целевого UUID,
не обычной миграцией и не удалением общей базы.

## Роли и подключения

| Назначение | Роль PostgreSQL | Подключение |
| --- | --- | --- |
| Бизнес-запросы и workers | `nervion_data` | PgBouncer, `nervion_data_1` |
| Платформенный API | `nervion_platform` | PgBouncer, `nervion_platform` |
| Миграции бизнес-данных | `nervion_data_migrator` | PostgreSQL напрямую |
| Миграции платформы | `nervion_platform_migrator` | PostgreSQL напрямую |

Runtime-роли не владеют таблицами, не наследуют владельцев и не имеют `SUPERUSER`,
`BYPASSRLS`, `CREATEDB`, `CREATEROLE`, `TRUNCATE` или права создавать таблицы.
Пароли миграций передаются только migration job. Не добавляйте их в окружение
работающих frontend/backend/worker.

Для backend укажите `POSTGRES_*` и `PLATFORM_POSTGRES_*` с портом PgBouncer.
Для миграций задайте `MIGRATION_POSTGRES_*` и `PLATFORM_MIGRATION_POSTGRES_*`
с прямым портом PostgreSQL. `JWT_SECRET` обязателен и одинаков для всех реплик.
`TENANCY_PROXY_SECRET` должен совпадать у backend и серверной части Nuxt.
`REDIS_URL` обязателен для обмена WebSocket-событиями между репликами.
Полный перечень переменных находится в `apps/backend/.env.example`.

Для уже собранного Nuxt `.output` задавайте runtime-переменные с префиксом Nuxt:
`NUXT_PUBLIC_TENANCY_ENABLED=true`, `NUXT_PUBLIC_TENANCY_ROOT_DOMAIN`,
`NUXT_PUBLIC_PLATFORM_ADMIN_HOST`, `NUXT_TENANCY_PROXY_SECRET`,
`NUXT_TENANCY_ALLOWED_HOSTS` и `NUXT_API_INTERNAL_URL`. Переменные без префикса
используются при dev/build и сами по себе не меняют конфигурацию готовой сборки.

Для внутренней админки задайте `PLATFORM_ADMIN_EMAIL` и
`PLATFORM_ADMIN_PASSWORD_HASH`. Хеш генерируется локально, пароль передается
через stdin из менеджера секретов, а не аргументом командной строки:

```bash
pnpm --filter backend exec ts-node src/platform/hash-admin-password.ts
```

CLI ожидает пароль длиной 12-256 символов и EOF, затем выводит scrypt hash.
Сохраните результат в secret store, не в git. По умолчанию админка доступна
только на `admin.nervion.ru`; домен меняется через `PLATFORM_ADMIN_HOST`.

PgBouncer работает в `transaction` pooling. Tenant устанавливается только через
`set_config('app.tenant_id', tenantId, true)` внутри транзакции. Завершение транзакции
сбрасывает значение. Конфигурация также выполняет `DISCARD ALL` при возврате
подключения. Нельзя использовать сессионный `SET app.tenant_id`, session advisory
locks и временные таблицы между разными транзакциями.

## Инфраструктура для разработки и staging

`docker-compose.saas-infra.yml` поднимает только PostgreSQL, PgBouncer и Redis.
Это отдельные volumes, порты доступны только через loopback. Frontend и backend
запускаются обычными dev-командами проекта. Конфигурация не включает HA и архив WAL.

В каталоге вне репозитория подготовьте пять файлов с разными случайными паролями:
`postgres_password`, `data_password`, `platform_password`,
`data_migrator_password`, `platform_migrator_password`. Для совместимости с
PgBouncer используйте минимум 32 символа из `A-Z`, `a-z`, `0-9`, `_`, `-`.
Передайте абсолютный путь в `SAAS_SECRETS_DIR`. Пример запуска:

```bash
docker compose -f docker-compose.saas-infra.yml up -d
```

Прямой PostgreSQL доступен на `127.0.0.1:5433`, PgBouncer на `127.0.0.1:6432`,
Redis на `127.0.0.1:6380`. Порты переопределяются через `SAAS_POSTGRES_PORT`,
`SAAS_PGBOUNCER_PORT`, `SAAS_REDIS_PORT`.

Bootstrap в `deploy/saas/postgres/bootstrap.sql` выполняется только на пустом
volume. Он создает две базы и четыре ограниченные роли. Повторный запуск Compose
не меняет пароли и не обновляет схему существующей базы. Эти изменения выполняет
оператор отдельно. Нельзя направлять этот bootstrap на действующий production
кластер без адаптации и проверки владельцев существующих объектов.

## Переход существующего пространства

Переход выполняется сначала на восстановленной копии. Остановите запись,
планировщики и старые backend/SMTP-процессы на время переноса. Сохраните проверенную
резервную копию обеих баз и конфигурации файлового хранилища.

1. Создайте platform database и отдельные runtime/migration роли. Для текущей
   бизнес-базы можно сохранить существующее физическое имя, указав его в
   `POSTGRES_DB`; `data_1` остается логическим идентификатором shard.
2. Передайте владение бизнес-базой, схемой, таблицами, последовательностями,
   типами и функциями data migrator.
   Runtime-роль не должна быть прежним владельцем или его участником. Изменение
   владельцев существующего кластера требует отдельной проверки оператором.
3. Задайте стабильный UUID `TENANCY_BOOTSTRAP_TENANT_ID`,
   `TENANCY_BOOTSTRAP_SLUG`, `TENANCY_BOOTSTRAP_HOSTNAME` и `TENANCY_ENABLED=true`
   в окружении migration job. Один UUID используется всеми следующими шагами.
   `TENANCY_ROOT_DOMAIN` задает корневой домен новых клиентов. До миграции у
   активных пользователей должны быть email и пароль; дубли email без учета
   регистра и OAuth-only учетные записи требуют отдельного исправления.
   Для прежних HMAC-SHA1 паролей сохраните прежний активный `JWT_SECRET`: тот же
   секрет из окружения или ранее сохраненного `app_secrets.jwt_secret`. При
   переходе его нельзя заменять новым, иначе прежние пароли перестанут работать.
   Оператор переносит значение в secret store без вывода в git, терминальные
   логи или документацию. После успешного входа старый hash автоматически
   заменяется на scrypt. Bootstrap требует `JWT_SECRET`, если обнаружены такие
   пароли.
4. Примените миграции в указанном порядке:

```bash
pnpm --filter backend migration:run
pnpm --filter backend migration:platform:run
pnpm --filter backend migration:tenant:run
pnpm --filter backend tenant:bootstrap
```

В production-образе команды выполняются через скомпилированные entrypoints:

```bash
node node_modules/typeorm/cli.js -d dist/data-source.js migration:run
node node_modules/typeorm/cli.js -d dist/platform/platform-data-source.js migration:run
node node_modules/typeorm/cli.js -d dist/tenant-data-source.js migration:run
node dist/platform/bootstrap-existing-tenant.js
```

5. Выполните перенос файлов командой `tenant:storage:migrate` по разделу ниже,
   затем проверьте существующие вложения, аватары и rich-text документы.
6. Настройте поддомены, HTTPS и проксирование. Прокси должен сохранять исходный
   hostname и удалять неподтвержденные служебные заголовки клиента.
7. Запустите SaaS backend с runtime credentials, Nuxt и проверку двух пространств.
   Создание второго клиента разрешается только после тестов изоляции.

Tenant migration выполняется в одной транзакции и берет эксклюзивные блокировки.
При ожидании блокировки более 15 секунд операция прерывается. Она добавляет и
заполняет `tenant_id`, перестраивает первичные и уникальные ключи, включая
expression/partial indexes, и внешние ключи. `ON DELETE SET NULL` сбрасывает только
поле связи, сохраняя `tenant_id`. Текущие числовые ID и sequences сохраняются.
После этого включаются `ENABLE/FORCE ROW LEVEL SECURITY` и точечные права runtime.

Таблицы миграций, `typeorm_metadata` и старый `app_secrets` не относятся к tenant
данным и недоступны data runtime. Предсуществующие RLS policies, views,
partitioned tables, exclusion constraints и связи вне бизнес-схемы приводят к
отказу миграции и требуют отдельной проверки. Миграция не изменяет их молча.

`migration:revert` для tenant-конверсии запрещен: после появления второго клиента
удаление изоляции небезопасно. Откат выполняется восстановлением резервной копии
в отдельный кластер с переключением приложения после проверки.

## Последующие изменения схемы

### Перенос файлов существующего клиента

Укажите тот же `TENANCY_BOOTSTRAP_TENANT_ID`, что при миграции базы. Задайте
`TENANCY_STORAGE_SOURCE_PREFIXES` явным списком принадлежащих приложению
префиксов, например `tracker-tasks/,tracker-chat/,tracker-avatars/,tracker-project-wiki/,crm/,mailbox/`.
Список примера не заменяет инвентаризацию бакета. Нельзя включать файлы других
приложений или клиентов. Пустой список и префикс `tenants/` запрещены.
Используются обычные `AWS_*` настройки S3. Сначала получите план без изменений:

```bash
pnpm --filter backend tenant:storage:migrate --dry-run
```

Команда выводит JSONL с исходным ключом, назначением, размером и ETag. Храните
этот вывод вне репозитория: имена файлов могут содержать клиентские данные.
Сравните список с ожидаемым объемом и остановите все источники записи.
Затем установите `TENANCY_STORAGE_WRITES_STOPPED=true` и выполните:

```bash
pnpm --filter backend tenant:storage:migrate --apply
```

Объекты копируются в `tenants/{TENANCY_BOOTSTRAP_TENANT_ID}/{старый-ключ}` с
private ACL. Оригиналы сохраняются. Крупные объекты копируются частями. Повторный
запуск сверяет размер и маркер исходного ETag; несовпадающее назначение вызывает
ошибку без перезаписи. После копирования сверяются размер и metadata. Во время
копирования source ETag фиксируется условием, чтобы не принять измененный файл.

Для ссылок, сохраненных в БД, задайте `TENANCY_STORAGE_PUBLIC_BASE_URLS` точным
списком старых публичных адресов, например `https://bucket.s3.example.com`.
Команда работает с migration credentials `MIGRATION_POSTGRES_*` и `POSTGRES_DB`.
После резервной копии БД сначала просмотрите dry-run, затем примените:

```bash
pnpm --filter backend tenant:storage:migrate --dry-run --rewrite-urls
pnpm --filter backend tenant:storage:migrate --apply --rewrite-urls
```

Меняются только строки указанного tenant и ссылки на объекты из проверенного
списка копирования. Обрабатываются поля `photo_url`, `description`, `message`,
`content`, `document`, `coverImage`, `cover_image`, а также `html_body` и
`text_body` таблицы `mail_messages`. JSON обходится рекурсивно. В строках
обрабатываются ссылки внутри HTML, Markdown и обычного текста, включая
`notifications.message`. Ссылки становятся относительными `/api/files/raw?key=...`.
Origin и путь старого хранилища должны точно соответствовать настроенным базам,
а декодированный ключ должен присутствовать в списке копирования. Чужие домены,
префиксы и нескопированные объекты не меняются. Параметры URL и fragment
сохраняются; ссылки с собственным параметром `key` оставляются без изменения,
чтобы не подменить ключ файлового API. HTML-разделители `&amp;` сохраняются.
Изменения БД применяются одной транзакцией. При ошибке копии S3 сохраняются и
повторный запуск продолжает перенос без удаления оригиналов.

Содержимое S3-документов переписывается отдельным шагом после копирования.
Задайте `TENANCY_STORAGE_REWRITE_KEYS_JSON` явным JSON-массивом исходных ключей
проверенных документов. Каждый ключ должен входить в выбранные source prefixes
и иметь проверенную tenant-копию. Этот шаг принимает только несжатые UTF-8 JSON
документы размером до 16 МиБ. Форматирование, числовая точность и имена JSON-полей
сохраняются; меняются только строковые значения. Для остальных форматов нужен
отдельный перенос содержимого.

```bash
pnpm --filter backend tenant:storage:migrate --dry-run --rewrite-documents
pnpm --filter backend tenant:storage:migrate --apply --rewrite-documents
```

Флаги `--rewrite-documents` и `--rewrite-urls` выполняются раздельно. Dry-run
использует только чтение S3 и не проверяет поддержку PUT. Применение по-прежнему
требует остановленных записей и `TENANCY_STORAGE_WRITES_STOPPED=true`.
До записи документов команда проверяет условный PUT: запрос с заведомо неверным
`IfMatch` направляется в уникальный отсутствующий ключ
`tenants/{tenantId}/.nervion-migration-probes/`. Продолжение допускается только
после ответа 404 или 412. Если провайдер игнорирует условие, команда останавливается
и оставляет только изолированный пустой probe-объект; документы не изменяются.
Другие ошибки также останавливают шаг. Безусловного PUT как fallback нет.

Переписывается только `tenants/{tenantId}/{исходный-ключ}`. Исходный объект
остается неизменным. Перед записью сверяются fingerprint исходного ключа,
ETag и размера, содержимое исходника и текущей копии. Запись использует `IfMatch`
с ETag копии, затем проверяются размер и SHA-256 полученного объекта. Metadata
связывает результат с tenant, исходным fingerprint, исходным размером и SHA-256.
Повторный запуск как copy-, так и rewrite-шагов принимает переписанную копию
только после проверки этих полей и актуального содержимого. Измененная копия
или исходник вызывают отказ без перезаписи.

Production entrypoint: `node dist/storage/migrate-tenant-storage.js` с теми же
флагами. После проверки отключите публичное чтение бакета/CDN и старых объектов.
Private ACL новых объектов недостаточно, если bucket policy продолжает разрешать
публичный GET. Runtime никогда не читает старые глобальные ключи как fallback.
Если бакет используется другими приложениями, сначала проверьте их префиксы и
зависимости. Закрытие публичного чтения общего бакета не входит в команды мигратора.

### Изменения таблиц

Любая новая бизнес-таблица создается с `tenant_id uuid NOT NULL`, tenant-scoped
ключами, внешними ключами и `FORCE ROW LEVEL SECURITY` в той же миграции.
Права runtime выдаются только после установки политики. Автоматических grants
на новые таблицы в data database нет.

Миграционная роль тоже имеет `NOBYPASSRLS`. Изменения данных существующей tenant
таблицы выполняются с явным tenant context для каждого клиента. Нельзя считать,
что владелец таблицы видит все строки после `FORCE ROW LEVEL SECURITY`.
При обновлении с tenant schema не запускайте старые миграции и `synchronize`.

Фоновые задания находятся в `tenant_jobs`. Ключ идемпотентности уникален внутри
tenant, таблица защищена той же RLS, индекс выбирает готовые pending-задания
конкретного клиента. Задание содержит shard, actor, kind и payload.
Процесс забирает только те `kind`, для которых зарегистрирован обработчик.
Перед каждым заданием повторно проверяются статус, срок оплаты и флаги клиента.
Клиенты обслуживаются по очереди, по одному заданию за круг, до 20 кругов.
`TENANT_JOBS_CONCURRENCY` ограничивает число параллельно обслуживаемых клиентов
(по умолчанию 4, допустимо 1-16). Учитывайте его при настройке `DB_POOL_MAX`,
оставляя соединения для HTTP и почтовой очереди.
`TENANT_JOBS_WORKER_ENABLED=false` отключает цикл исполнения, не HTTP API.
Отдельный SMTP-процесс устанавливает это значение автоматически.
Почтовая очередь имеет собственный цикл и фиксирует claim до внешней отправки.

После обновления существующей SaaS-инсталляции выполните
`migration:tenant:run` для каждого data shard до запуска новой версии.
Миграции добавляют `mail_outbox` с составной связью и `FORCE RLS`, статусы
исходящих сообщений и индекс очистки завершенных заданий мониторинга.
Старую миграцию конверсии повторно запускать не нужно. Новые таблицы должны
пройти проверку изоляции и восстановления так же, как первоначальная схема.

Долгое WebSocket-соединение хранит проверенный при подключении hostname.
Истечение короткой подписи SSR/ingress не меняет его tenant. Голос повторно
проверяет JWT, membership, состав комнаты и feature flag во время сессии.
Redis и Git volume доступны только доверенным серверным процессам. Логи
прокси не должны содержать тела запросов, PAT, cookie или секреты webhook.

Сначала все клиенты используют `data_1`. `DATA_SHARDS_JSON` позволяет добавить
подключения без изменения публичного API. Запись нескольких баз в одном
PostgreSQL не добавляет ему CPU/IOPS. При нехватке ресурсов новый shard размещается
в отдельном кластере; автоматический перенос существующих данных не выполняется.

## Проверки перед подключением клиента

Интеграционный тест `tenant-isolation.integration.spec.ts` проверяет базу под
непривилегированной ролью: отсутствие доступа без tenant, одинаковые ID и unique
значения в разных пространствах, составные FK, SET NULL, CASCADE, выражения и
частичные индексы, запрет TRUNCATE, очистку контекста после commit/rollback.

Для теста подготовьте пустую disposable database с именем
`nervion_tenant_test_<suffix>`, владельцем data migrator, и выдайте runtime-роли
CONNECT/USAGE. Не используйте production database. Тест оставляет схему для
проверки; повторный запуск требует новой пустой базы.

```bash
pnpm --filter backend test -- --runInBand tenant-isolation.integration.spec.ts
```

Передайте `TENANCY_TEST_DATABASE_URL` для прямого подключения миграционной роли и
`TENANCY_TEST_RUNTIME_DATABASE_URL` для runtime-роли той же базы. Без переменных
suite пропускается. Повторите на второй пустой базе с runtime URL через PgBouncer;
в `[databases]` заранее добавьте только эту конкретную тестовую базу, без wildcard.

`tenant-full-schema.integration.spec.ts` отдельно применяет все бизнес-миграции
и три tenant-миграции к новой пустой базе, затем проверяет реальные TypeORM-сущности,
many-to-many таблицы, сохранение и чтение связей, удаление и проверку этапов задач.
Проверки включают `mail_outbox`: одинаковые ID в разных пространствах, составные
FK, каскадное удаление и отсутствие доступа без tenant context. Также проверяется
индекс очистки завершенных заданий мониторинга.
Для него задаются `TENANCY_FULL_SCHEMA_DATABASE_URL` и
`TENANCY_FULL_SCHEMA_RUNTIME_DATABASE_URL` с теми же требованиями к имени и ролям.
Для каждого запуска нужна новая пустая база.

Другие acceptance suites:

| Suite | Переменные окружения | Подготовка |
| --- | --- | --- |
| `platform/platform.integration.spec.ts` | `PLATFORM_TEST_DATABASE_URL`, `PLATFORM_TEST_RUNTIME_DATABASE_URL` | Одна пустая disposable database с `_test` в имени, разные migration/runtime роли. Suite создает ограниченную fixture схему и сохраняет ее после проверки; повторный запуск требует новой базы. |
| `tenancy/tenant-http.integration.spec.ts` | `TENANCY_HTTP_TEST_DATA_URL`, `TENANCY_HTTP_TEST_PLATFORM_URL`, `TENANCY_HTTP_TEST_REDIS_URL` | Две отдельные тестовые базы с примененными миграциями и runtime-ролями, отдельный Redis. Suite запускает настоящий AppModule, данные созданных тестовых клиентов сохраняет для проверки. |

```bash
pnpm --filter backend exec jest --runInBand src/platform/platform.integration.spec.ts
pnpm --filter backend exec jest --runInBand src/tenancy/tenant-http.integration.spec.ts
```

Platform suite проверяет конкурентный лимит мест, общие учетные записи,
подтверждение владения email, повторный provisioning и окончание оплаты.
HTTP suite проверяет создание и вход двух клиентов через API, изоляцию CRUD,
JWT/Host/Origin, read-only, включение четырех модулей отдельно для каждого клиента
и контекст/идемпотентность фоновых заданий. Без своих
переменных интеграционные suites пропускаются; успешный обычный Jest без них
не заменяет acceptance на PostgreSQL и Redis.

PgBouncer проверяется той же SQL suite на новой базе. Установите
`pool_mode=transaction`, `pool_size=1`, `max_db_connections=1`, выполните запросы
обоих tenants и убедитесь, что `pg_backend_pid()` одинаков, а запрос без tenant
после `COMMIT` и `ROLLBACK` возвращает ноль строк. Эта проверка выполнена для
добавленного Dockerfile и PostgreSQL 17.

Полный приемочный прогон дополняется проверками WebSocket, SSR и файлов на
реальных transport и storage. Успех SQL и HTTP suites не подтверждает изоляцию
всех остальных прикладных каналов.

Локальный прогон 2026-10-30 после добавления четырех модулей:

- Backend: 55 suites, 494 теста прошли; пять интеграционных suites в этом запуске
  пропущены, поскольку требуют отдельного окружения.
- Полная схема на отдельной базе: 6 тестов прошли; все 51 бизнес-таблица имеют
  `FORCE RLS`, применены миграции outbox и очистки заданий мониторинга.
- SQL-изоляция: 7 тестов прошли напрямую в PostgreSQL и еще 7 через отдельный
  PgBouncer с transaction pooling и одним серверным соединением.
- Сборка общих контрактов, проверка типов и сборка backend прошли.
- Frontend: 32 теста, проверка типов и production build прошли. Сохранились
  предупреждения об устаревшей базе Browserslist и чанках больше 500 kB.

Дополнительный прогон перед подготовкой препрода: platform suite 7/7, HTTP suite
6/6 прошли на новых тестовых базах и отдельном Redis. Проверено включение четырех
модулей отдельно для каждого клиента. Рабочие базы и текущий preview не затронуты.

На отдельном тестовом стенде прошли девять сквозных проверок: вход оператора и
двух клиентов, отказ с чужим JWT, изоляция проектов, реальные WebSocket-события,
загрузка и чтение приватных файлов, отключение AI и Web Push, флаги интеграций и
режим чтения. При запросе отсутствующего файла проверяется 404, а не 500.
Логические дампы обеих баз восстановлены в новые тестовые базы: совпали число
строк, tenant-данные и флаги RLS всех 51 бизнес-таблицы. Это не проверка PITR или HA.

Реальные почтовые провайдеры, внешние Git-сервисы, звонки WebRTC/TURN и цели
мониторинга в этом прогоне не подключались. Их сквозная приемка остается
отдельным этапом перед включением клиентам.

## Переход существующего автодеплоя

Перед первым SaaS-релизом проверьте hook и release runner самого Нервиона.
Сохранение старого hook без проверки опасно: следующий push может запустить
self-hosted backend или SMTP против уже перенесенных данных. Хуки внешних
клиентских проектов не относятся к этой операции и остаются без изменений.

Новый путь релиза должен использовать точный принятый commit SHA, готовые образы
по immutable digest и блокировку параллельных запусков. Прием push и успешность
релиза учитываются отдельно. Сборка выполняется вне production. Миграции
запускаются отдельным job с migration-role, не при старте runtime.

Обновляйте только явно перечисленные SaaS-сервисы в отдельном compose project.
Общий PostgreSQL и ingress не должны пересоздаваться побочным действием
`docker compose up`. До переключения ingress нужны проверки здоровья и
приемочные сценарии; текущие образы, конфигурация и свежий backup сохраняются.

Возврат к старой базе допустим только до разрешения записи в SaaS. После новых
записей простой возврат ingress потеряет изменения пользователей. Нужен отдельный
план согласования данных или восстановление новой системы. Старый автоматический
deploy не включается обратно как способ отката.

## Резервное копирование и отказоустойчивость

Один кластер объединяет отказ platform и data database. Production требует managed
HA или реплики с проверенным переключением, автоматических физических backups и
непрерывного архива WAL для PITR. Compose-пример этого не предоставляет. Параметры
архива, хранилище резервных копий и учетные записи задаются оператором вне git.

Для собственного PostgreSQL настройте pgBackRest или WAL-G: base backup ежедневно,
непрерывный WAL archive, отдельное хранилище, шифрование, минимум 14 дней истории.
Файлы S3 защищаются versioning и отдельной политикой резервирования. Снимок базы
не является резервной копией вложений.

Проверка восстановления проводится на изолированном кластере ежемесячно и перед
сменой схемы изоляции: восстановить base backup и WAL до выбранного времени,
проверить обе базы, владельцев, RLS, memberships и доступность вложений. Зафиксировать
время восстановления и возможную потерю данных. Не подключать тестовый кластер к
production-почте, Web Push и внешним интеграциям.

Для текущей схемы также проверено логическое восстановление `pg_dump -Fc` и
`pg_restore` в новую пустую тестовую базу: совпали данные клиентов, все 50
бизнес-таблиц сохранили `FORCE RLS`, runtime без tenant не получил строки.
Этот результат относится к схеме до добавления `mail_outbox`. Для обновленной
схемы и четырех интеграций нужен отдельный приемочный прогон, он не заменяется
результатами предыдущей версии.
Это проверка backup/restore схемы приложения; PITR из WAL и переключение HA
проверяются отдельно на выбранной production-инфраструктуре.

Алерты: нет успешного backup 24 часа, отстает WAL archive/реплика, заканчивается
диск, растут ожидания PgBouncer, занято более 80% лимита connections, ошибки
изоляции и provisioning. Устойчивая загрузка CPU/IOPS/диска около 70% служит
поводом для измерения запаса и планирования нового кластера. Высокое использование
RAM само по себе не означает перегрузку PostgreSQL, поскольку память занята кешем.

Справка: [PostgreSQL RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html),
[составные внешние ключи](https://www.postgresql.org/docs/17/sql-createtable.html),
[PgBouncer transaction pooling](https://www.pgbouncer.org/config.html).
