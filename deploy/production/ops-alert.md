# Аварийные уведомления

`ops-alert.py` отправляет фиксированное error-событие в выбранный оператором
Sentry/GlitchTip. Поддержаны только четыре unit: `nervion-backup.service`,
`nervion-backup-monitor.service`, `smtp-cert-sync.service`,
`nervion-infra-monitor.service`. Произвольного текста,
journal, env, PID, hostname, traceback, пользовательских данных и ключей в event
нет. DSN используется только для HTTPS destination и transport authentication.

Установка выполняется отдельно после выбора получателя:

1. Сохранить существующий DSN в отдельном root-owned файле
   `/etc/nervion-ops/sentry-dsn`, права `0600`, вне checkout. Разрешены HTTPS,
   DNS hostname, порт 443 и числовой project ID. Deprecated secret в URL,
   query/fragment, IP literal и небезопасные файлы отклоняются.
2. Адаптировать `nervion-ops-alert@.service.example`, проверить путь к helper.
   Unit получает файл через `LoadCredential`, не через env/argv.
   Установить шаблон до включения связанных backup/SMTP timers.
3. Настроить rule и получателя в существующем проекте Sentry/GlitchTip, включая
   частоту повторов. Проверить доставку одним отдельно согласованным smoke event.
   Успешный HTTP-ответ helper означает прием события, не доставку письма человеку.

OnFailure уже указан в четырех service templates. Helper проверяет системную
TLS-цепочку и hostname, не следует redirects, не использует proxy/CA из env,
не читает тело ответа. Две попытки максимум, одна и та же event ID; сетевой
таймаут 5 секунд, общий deadline 15 секунд, systemd timeout 20 секунд. HTTP 4xx,
429 и TLS-ошибки не повторяются. При недоступности receiver unit завершается
ошибкой без рекурсивного OnFailure. Локальной durable-очереди нет.

GlitchTip на том же VDS не обнаружит полное отключение этого VDS. Нужна отдельная
внешняя проверка доступности; эта интеграция не является HA или off-host monitor.
Журналы и private state сохраняются локально для оператора. Helper не подключает
получателей, не изменяет email transport и не включает timers автоматически.

Каждая новая активация OnFailure получает отдельный fingerprint с новым event ID.
Это важно для GlitchTip, где повторное событие уже уведомленной issue может не
породить новое письмо. Повтор HTTP-запроса внутри одной доставки использует тот
же event ID и fingerprint. Служебный код проверки остается постоянным тегом.
Частота новых аварийных писем зависит от запуска связанных service/timer и правил
проекта; helper не обещает exactly-once доставку email и не подавляет повторный
сбой после первой аварии.

## Проверка инфраструктуры

Существующий `postgres/backup-job.sh monitor` проверяет repository status,
шифрование, возраст последней копии до 36 часов и full до 8 дней. Он не проверяет
текущий WAL backlog, диск, RAM и SMTP expiry. Для них предназначен отдельный
`infra-monitor.py`, service и timer с периодом 5 минут. Он ничего не исправляет,
не запускает контейнеры, не делает restart и не обращается к рабочим HTTP-целям.

Установка выполняется оператором после готовности PostgreSQL и SMTP bundle:

1. Скопировать helper в путь из `nervion-infra-monitor.service.example`.
   Создать root-owned config `0600` по `infra-monitor.config.example.json`.
   Указать точный Compose project, service `postgres`, каталоги Docker/данных,
   отдельный state directory `0700`. Пароли и DSN этому helper не нужны.
2. Если SMTP используется, указать `smtpBundleDirectory` и `smtpHostname`.
   Без обоих полей проверка сертификата отключена. Если поля заданы, отсутствие
   bundle или неверный hostname считаются ошибкой. Читается только публичный
   `current/fullchain.pem`, не ключ и не Caddy storage.
3. Проверить `--check-config`, установить service/timer и OnFailure template,
   выполнить `systemd-analyze verify`. Включать timer только после проверки
   готовности целевого контура. Установка файлов сама по себе timer не запускает.

Порог диска: доступно меньше 4 GiB или занято не меньше 90%. Проверяются
настроенные каталоги и data volume только своего PostgreSQL. RAM: host
`MemAvailable` меньше 256 MiB в трех последовательных измерениях с интервалом
240-660 секунд. Быстрые ручные повторы не увеличивают счетчик; пропуск измерений
или восстановление сбрасывает его. Краткие CPU bursts не создают уведомлений.

WAL: ожидающий `.ready` старше 300 секунд, неустраненная ошибка archiver,
выключенная архивация или объем WAL больше 1 GiB. Давний `last_archived_time`
у idle PostgreSQL сам по себе не является сбоем. Выполняется только фиксированный
read-only запрос системных агрегатов с statement timeout 3 секунды и lock timeout
1 секунда. Проверяются project/service labels, running state, ID и принадлежность
data volume. Чужой, отсутствующий или неоднозначный контейнер отклоняется.

Сертификат SMTP: совпадение hostname и срок больше 14 дней у публичного локального
bundle. Это не проверка внешней доступности STARTTLS, цепочки доверия клиента или
доставки писем. Непрочитанные private key и рабочие данные в alert не попадают.

Первый новый код состояния вызывает `OPS_INFRA_HEALTH_FAILED`; неизменный код
повторяется не чаще раза в 6 часов. Восстановление снимает подавление, новый код
может вызвать отдельную попытку сразу. Локальный state `0600` обновляется атомарно
под file lock перед попыткой уведомления. Это ограничение попыток, не гарантия
доставки: при недоступном GlitchTip повтор будет по следующему напоминанию.
В alert отправляется только общий фиксированный код; конкретные безопасные коды
проверок остаются в локальном выводе и state. Ошибка самого config/state или
общего deadline завершается аварийно без подавления и требует ремонта оператором.

Общий deadline 45 секунд, subprocess timeout до 8 секунд, systemd timeout
55 секунд, память helper ограничена 96 MiB, TasksMax 64 учитывает потоки Docker CLI.
Проверки не читают журналы, env,
SQL-пользовательские данные или объектное хранилище. Runtime-ролям приложения
не выдаются дополнительные права. CPU, inode, внешний uptime и container OOM
этот bounded monitor не проверяет. Проверка на том же VDS не заменяет внешний
монитор и не обнаружит полное отключение хоста.
